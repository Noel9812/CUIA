# 2. Product Vision

## Vision Statement

The Capacity & Utilization Intelligence Agent (CUIA) is an AI-assisted workforce intelligence platform that transforms operational engineering data into actionable management insights.

Instead of functioning as a reporting application, CUIA operates as a decision-support platform that continuously analyzes engineering activity, identifies workforce trends, detects operational risks, and presents explainable recommendations to management.

The platform combines deterministic analytics with conversational AI to help engineering leadership make informed workforce planning decisions.

---

## Business Problem

Engineering organizations often struggle to answer questions such as:

- Which engineers are overloaded?
- Which engineers are underutilized?
- Why is utilization decreasing?
- Are sprint estimates accurate?
- Which teams are approaching capacity limits?
- Which critical skills depend on a single individual?
- What staffing risks exist?
- What corrective actions should managers take?

These answers are typically spread across multiple Jira boards, reports, spreadsheets, and manual calculations.

Managers spend significant time gathering data instead of making decisions.

---

## Proposed Solution

CUIA centralizes engineering operational data and converts it into meaningful insights through:

- Automated Jira data ingestion.
- Deterministic analytics calculations.
- Workforce health monitoring.
- Capacity analysis.
- Productivity analysis.
- Forecasting.
- AI-assisted explanations.
- Executive dashboards.
- Team dashboards.

The AI component explains existing analytics but never replaces the deterministic analytics engine.

---

## Product Philosophy

The platform follows five core principles.

### 1. Analytics Before AI

Analytics are always produced by deterministic Python code.

Artificial Intelligence explains analytics but never calculates them.

---

### 2. Security First

Every request must pass through authentication, authorization, RBAC validation, and team scope enforcement before any data is processed.

Security is enforced entirely on the backend.

---

### 3. Explainable Intelligence

Every recommendation generated by the platform must be explainable.

Users should always understand:

- Why a recommendation was made.
- Which data contributed to the recommendation.
- Which analytics support the conclusion.

---

### 4. Enterprise-Oriented Design

Although this project is a Proof of Concept, the architecture should follow enterprise engineering practices.

The solution should demonstrate:

- Clean architecture.
- Layered design.
- Modular implementation.
- Secure integrations.
- Extensible data models.
- Strong governance.

---

### 5. Future-Ready Architecture

The POC intentionally implements only the functionality necessary for demonstrating business value.

However, architectural decisions should avoid preventing future expansion.

Examples include:

- Multi-tenancy.
- Additional identity providers.
- HR system integration.
- Microsoft Teams integration.
- Multiple AI providers.
- Advanced forecasting.

These capabilities are intentionally deferred and must not influence the implementation complexity of the POC.

# 9. Identity & Access Management Baseline

## Purpose

Identity and access management ensures that:

- Only authorized users can access the platform.
- Every request is authenticated.
- Every request is authorized.
- Users can only access data within their permitted organizational scope.
- The AI Copilot cannot expose data outside the authenticated user's permissions.

Authentication and authorization are treated as two separate responsibilities.

---

## Identity Principles

The platform follows these identity principles:

- Authentication verifies **who the user is**.
- Authorization determines **what the user can access**.
- Team scope determines **which organizational data the user can see**.
- Every request must pass all three stages before any analytics or AI processing occurs.

The frontend is never trusted to enforce permissions.

The backend remains the single source of truth for authorization.

---

# 10. Authentication Baseline

## Authentication Provider

The platform uses:

**Microsoft Entra ID**

for user authentication.

No local username/password authentication is implemented.

---

## Tenant Model

The application is configured as:

**Single Tenant**

Only users belonging to the organization's Microsoft Entra tenant can authenticate.

Users from external Microsoft tenants cannot access the application.

Personal Microsoft accounts are not supported.

---

## Authentication Flow

```text
User Opens Application
        │
        ▼
Clicks "Sign in with Microsoft"
        │
        ▼
Redirect to Microsoft Entra ID
        │
        ▼
User Authenticates
        │
        ▼
Microsoft Returns ID Token
        │
        ▼
Backend Validates Token
        │
        ▼
Backend Looks Up Internal User
        │
        ▼
RBAC Resolution
        │
        ▼
Team Scope Resolution
        │
        ▼
Dashboard Access Granted
```

---

## Token Validation

Every token must be validated for:

- Signature
- Issuer
- Audience
- Expiration
- Tenant ID
- User Object ID (OID)
- Email Address

Invalid tokens are rejected immediately.

---

## Session Principles

Authentication only proves identity.

It does **not** determine authorization.

After authentication, the backend must always load:

- Internal User
- Assigned Role
- Team Memberships
- Manager Relationships
- Account Status

Only then can access be granted.

---

# 11. Authorization Baseline

## Authorization Philosophy

Authorization is entirely owned by CUIA.

Microsoft Entra ID only confirms identity.

CUIA determines:

- User role
- Organizational scope
- Team memberships
- Dashboard access
- API permissions
- AI permissions

---

## Authorization Pipeline

Every request follows this sequence:

```text
Authenticated User
        │
        ▼
Lookup Internal User Record
        │
        ▼
Check Account Status
        │
        ▼
Determine User Role
        │
        ▼
Resolve Team Scope
        │
        ▼
Validate Requested Resource
        │
        ▼
Execute Business Logic
        │
        ▼
Return Authorized Response
```

No business logic executes before authorization succeeds.

---

## Account Status

Every internal user has one of the following statuses:

- Active
- Inactive
- Suspended

Only Active users may access the platform.

Inactive or Suspended users are denied access even if they authenticate successfully through Microsoft Entra ID.

# 13. Organizational Model

The organizational model supports flexible team structures.

---

## Team Principles

The platform recognizes:

- Teams
- Managers
- Engineers

Each entity is managed independently.

---

## Manager-to-Team Relationship

A Delivery Manager may manage:

- One team
- Multiple teams

Each team may also have:

- One manager
- Multiple managers

Therefore:

**Manager ↔ Team is Many-to-Many**

---

## Engineer-to-Team Relationship

Engineers may belong to:

- One team
- Multiple teams

Each team contains:

- One engineer
- Many engineers

Therefore:

**Engineer ↔ Team is Many-to-Many**

---

## Why Many-to-Many?

This reflects real engineering organizations where:

- Shared platform teams exist.
- Engineers support multiple projects.
- Managers oversee multiple delivery streams.
- Temporary assignments occur.
- Cross-functional squads are common.

The POC supports this model from the beginning.

# 31. Analytics Engine Design Principles

## Purpose

The Analytics Engine is the heart of the CUIA platform.

Its responsibility is to transform operational engineering data into reliable workforce intelligence.

All analytics must be deterministic, reproducible, explainable, and completely independent from the AI layer.

## Core Principles

The Analytics Engine shall always follow these principles:

1. Analytics are calculated only through Python business logic.
2. Every calculation must be deterministic.
3. Every result must be reproducible.
4. Every recommendation must reference supporting metrics.
5. Analytics never depend on LLM output.
6. Historical analytics must remain immutable.
7. Analytics execution must be versioned.

# 84. Final Vision Statement

The Capacity & Utilization Intelligence Agent (CUIA) is an AI-assisted workforce intelligence platform that transforms engineering execution data into actionable leadership insights.

The platform combines deterministic analytics, secure role-based access control, conversational AI, and executive dashboards to help organizations understand workforce health, optimize resource utilization, identify risks, and support better engineering management decisions.

The Proof of Concept focuses on delivering a robust, enterprise-oriented foundation that demonstrates the complete end-to-end workflow—from Jira data ingestion through analytics, recommendations, dashboards, and AI-assisted exploration—while maintaining strong security, governance, auditability, and clear architectural boundaries.

This baseline serves as the authoritative reference for all development activities throughout the POC.
