# 1. Purpose
This document defines the REST APIs exposed by the Capacity & Utilization Intelligence Agent (CUIA).
It specifies:
- API endpoints
- Request formats
- Response formats
- Authentication requirements
- Authorization rules
- Error handling
- Common API conventions
The API provides the communication layer between the frontend application and backend services.
It also serves as the contract between frontend and backend development.
---
# 2. API Overview
The backend exposes RESTful APIs that allow the frontend to:
- Authenticate users
- Retrieve dashboard data
- Synchronize Jira data
- Upload operational datasets
- Retrieve analytical results
- Interact with the AI Copilot
- Receive notifications
- Access application configuration
The backend is responsible for:
- Authentication validation
- Authorization
- Business logic
- Analytics retrieval
- AI orchestration
- Data persistence
The frontend never performs business calculations.
---
## API Consumers
The APIs are consumed by:
- React Frontend
- AI Copilot Interface
- Scheduled Background Jobs
- Future Integrations
---
## API Style
The application follows REST architectural principles.
Characteristics include:
- Resource-oriented URLs
- Stateless requests
- JSON request and response bodies
- Standard HTTP methods
- Standard HTTP status codes
---
# 3. API Design Principles
The API follows several guiding principles.
---
## Backend as Source of Truth
All business logic executes within the backend.
The frontend acts only as a presentation layer.
---
## Feature-Oriented APIs
Endpoints expose business capabilities rather than database tables.
For example:
```
GET /api/v1/dashboard/team
```
returns all data required by the Team Dashboard instead of requiring multiple independent API calls.
---
## Read-Optimized Analytics
Analytical data is generated by the Analytics Engine.
Frontend clients retrieve analytical results but never create or modify them.
---
## Consistent Response Structure
Every successful API returns a consistent response format.
This simplifies frontend implementation and error handling.
---
## Secure by Default
Protected APIs require:
- Valid authentication
- Role validation
- Team scope validation
Unauthorized data is never returned.
---
## Deterministic Data
Analytics APIs return deterministic analytical results.
The AI Copilot explains analytics but never modifies analytical data.
---

# 5. Authentication & Authorization
## Authentication
Authentication is delegated to Microsoft Entra ID.
The frontend authenticates users using Microsoft Entra ID and receives an access token.
The token is included with every protected request.
Example:
```
Authorization: Bearer <access_token>
```
The backend validates:
- Token signature
- Token expiration
- Issuer
- Audience
If validation succeeds, the authenticated user is resolved.
---
## Authorization
Authentication confirms **who the user is**.
Authorization determines **what the user is allowed to access**.
Authorization is enforced entirely by the backend.
The frontend must never be trusted to enforce permissions.
---
## Supported Roles
| Role | Access |
|------|--------|
| Delivery Manager | Team Dashboard, Team Analytics, Copilot, Forecast |
| Leadership | Executive Dashboard, Organization Analytics, Copilot, Forecast |
| Platform Admin | Users, roles, teams, mappings, integrations, configuration, audit and AI governance; analytics only per explicit scope policy |
---
## Team Scope
Delivery Managers may access only teams for which they have an active `team_managers` relationship; a request may select one or an aggregate subset of those teams.
Leadership users may access organization-wide aggregated information.
Every analytics request is filtered according to the authenticated user's scope before results are returned.

# 7. Response Standards
Every successful API follows a common response structure.
Example:
```json
{
  "success": true,
  "message": "Request completed successfully.",
  "data": {},
  "metadata": {}
}
```
---
## Response Fields
| Field | Description |
|--------|-------------|
| success | Indicates request success |
| message | Human-readable summary |
| data | Response payload |
| metadata | Pagination or additional information |
---
## Empty Responses
If no records exist, the API returns:
```json
{
  "success": true,
  "message": "No records found.",
  "data": [],
  "metadata": {}
}
```
Empty results are not considered errors.

# 13. Import & Synchronization APIs
This section defines the APIs responsible for importing operational data into the Capacity & Utilization Intelligence Agent.
Operational data is imported from external sources and stored within the application's operational data model.
Imported data serves as the input for the Analytics Engine.
Import APIs do not calculate analytics.
Analytical processing is initiated separately after successful data synchronization.

|----------|---------|

# Jira Synchronization APIs
---
## POST /api/v1/imports/jira/sync
### Purpose
Synchronizes operational data from Jira into the local application database.
The synchronization imports only the fields required by the application for workforce analytics.
Imported data includes:
- Issues
- Worklogs
- Assignees
- Estimates
- Priorities
- Status
- Resolution data
- Sprint information
---
### Authentication
Required
---
### Authorization
Leadership
Delivery Manager
---
### Request Body
No request body is required.
The Jira integration configured within the application is used automatically.
---
### Processing
The backend performs the following steps:
1. Connect to Jira REST API.
2. Retrieve configured project data.
3. Validate retrieved records.
4. Store operational data.
5. Record import history.
6. Return synchronization summary.
Analytics are **not** executed during this process.
---
### Success Response
```json
{
  "success": true,
  "message": "Jira synchronization completed successfully.",
  "data": {
    "issuesImported": 186,
    "worklogsImported": 932,
    "durationSeconds": 18
  },
  "metadata": {}
}
```
---
### Possible Status Codes
| Status | Meaning |
|---------|---------|
| 200 | Synchronization completed |
| 401 | Authentication failed |
| 403 | Access denied |
| 500 | Jira synchronization failed |

All API requests follow the same processing flow.
```text
HTTP Request
      │
      ▼

      │
      ▼

      ▼
```

| Layer | Responsibility |

| Domain Service | Business rules and domain logic |
| Repository | Data persistence and retrieval |
| Database | Persistent storage |
Controllers must never contain business logic or directly access the database.

```text

        │
        ▼
```

Example:
```text
CopilotService

        │
        ▼
Analytics Services
```

Modules must not bypass service boundaries by directly accessing another module's repositories or database tables.
